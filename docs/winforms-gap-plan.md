# `System.Windows.Forms` gap analysis

**Measured 2026-08-02** against the real `System.Windows.Forms.dll` from the .NET 10 WindowsDesktop
targeting pack, vs. a Release build of `Majorsilence.Forms.dll`.

This is the WinForms counterpart to [`gdi-gap-plan.md`](gdi-gap-plan.md), and it exists for the same
reason: [`COMPATIBILITY_MATRIX.md`](../COMPATIBILITY_MATRIX.md)'s WinForms audit was written by hand,
compared *names* against upstream's `PublicAPI.Shipped.txt`, and dated 2026-07-29 — the same shape of
audit that went stale on the drawing side within a release. The numbers here come from reflection over
the real assemblies and are regenerated by a committed tool, so they cannot rot.

## How it is measured

[`tools/Majorsilence.Forms.ApiDiff`](../tools/Majorsilence.Forms.ApiDiff) — the same tool that audits
the drawing surface, generalised to take a *surface* (upstream assembly + namespace map + exclusions).
Both surfaces share one scanner, so a fix to the comparison logic applies to both.

```
dotnet run --project tools/Majorsilence.Forms.ApiDiff -- --surface winforms          # regenerate
dotnet run --project tools/Majorsilence.Forms.ApiDiff -- --surface winforms --check  # CI gate
```

Loaded through `MetadataLoadContext`, so nothing executes and it runs on Linux despite
`System.Windows.Forms` being Windows-only at runtime. `System.Windows.Forms` maps to
`Majorsilence.Forms`, per [MIGRATION.md's table](../MIGRATION.md#namespace-mapping).

**Deliberately excluded** (not reported at all, because they are not goals): `AxHost` (ActiveX/COM
hosting), the Win32 message plumbing (`Message`, `IMessageFilter`, `IWin32Window`, `NativeWindow`,
`IWindowTarget` — there is no HWND or message pump here; backends deliver input through their own
neutral seam), and Windows-only OS integration (`SystemInformation`, `InputLanguage`, `OSFeature`,
`ImeContext`, `WindowsFormsSection`, `PowerStatus`).

**Overload checking is off for this surface for now.** With ~1,500 wholly-missing members, an overload
report on a type that is itself half-implemented is noise rather than signal. Turn it on
(`Surface.WinForms.IncludeOverloads`) once the `MEMBER` count is down — the drawing surface only earned
it after five phases.

## Baseline: 1,905 entries

| Kind | Count |
|---|---|
| `TYPE` — no equivalent at all | 288 |
| `MEMBER` — type exists, member does not | 1,491 |
| `VALUE` — enum member exists with a **different number** | **126** |

### The 126 `VALUE` entries are bugs, not gaps

This is the headline finding, and it is the same class of defect Phase 2 found on the drawing side
(where `StringFormatFlags.DirectionRightToLeft` and `DirectionVertical` were transposed): the member
exists, the code compiles and runs, and it silently means something else.

Samples from the first run:

| Enum | Ours | Upstream |
|---|---|---|
| `AccessibleRole.Default` / `.None` | 0 / −1 — **swapped** | −1 / 0 |
| `AutoCompleteSource.None` | 0 | 128 |
| `AutoCompleteSource.CustomSource` | 6 | 64 |
| `CloseReason.FormOwnerClosing` / `.ApplicationExitCall` | 6 / 5 — **swapped** | 5 / 6 |
| `CloseReason.TaskManagerClosing` | 1 | 4 |
| `Border3DStyle.Raised` | 2 | 5 |

`AutoCompleteSource` is the clearest hazard: it is a flags-style enum where `None` is `128` and
`CustomSource` is `64`, and ours numbers them sequentially from zero. Anything that round-trips the
*number* — a `.resx` resource, a persisted setting, interop — reads back a different member.

The worst offenders by count are the `DataGridView*` enums (10 in `DataGridViewCellBorderStyle` alone),
which is unsurprising: they are large enums that were plausibly hand-written from documentation rather
than from the real values.

**Fixing these is mechanical and should come first** — it is the highest-value, lowest-risk work in
this document, and there is a proven recipe: Phase 2 of the drawing plan generated every value from the
real assembly rather than transcribing it, precisely because transcription is how these got wrong.

### The 288 missing types

| Group | Count | Notes |
|---|---|---|
| `*EventHandler` delegates | 88 | One line each. Not optional: `public event DataGridViewCellEventHandler CellClick` does not compile without the delegate, and designer files wire events by delegate type. |
| `*EventArgs` | 54 | Mostly small data carriers. |
| Converters / attributes | 21 | Design-time; largely non-goals, consistent with the drawing surface. |
| Everything else | ~125 | The real work — see below. |

Among that last group, the ones that matter most for whether migrated code compiles are the **missing
base classes**: `ButtonBase`, `TextBoxBase`, `ListControl`, `UpDownBase`, `DataGridViewBand`,
`ToolStripDropDownItem`. A migrated app that declares `class MyButton : ButtonBase` fails outright, and
no amount of member-level work on `Button` fixes it.

Also absent: the `TaskDialog` family (12 types), the `WebBrowser` DOM (`HtmlDocument`, `HtmlElement`,
`HtmlWindow`, …), `ProfessionalColorTable`/`ProfessionalColors`, `SplitterPanel`, `ToolStripPanelRow`.

### The 1,491 missing members

Concentrated in a handful of large types:

| Type | Missing / total |
|---|---|
| `DataGridView` | 83 / 242 |
| `ToolStripItem` | 70 / 103 |
| `DataGrid`, `DataGridTableStyle` | 46, 42 |
| `ToolStripRenderer` | 41 / 41 |
| `TextBoxBase`, `ToolStripTextBox` | 38 each |
| `ListView` | 34 / 94 |
| `ToolStrip`, `Form` | 30 each |
| `Control` | 29 / 206 |

`DataGrid`/`DataGridTableStyle` are the .NET 1.x controls, superseded by `DataGridView` and rare in
modern code — low priority despite the count. `ToolStripRenderer` at 41/41 means the type is a shell:
custom ToolStrip rendering does not work at all.

## Progress

| Item | Status |
|---|---|
| 1 — the 126 `VALUE` mismatches | **Done.** All fixed, zero introduced; 24 tests. |
| 2 — delegates and event args | **Done.** 50 enums, 44 event-args, 79 delegates; 173 gaps closed. |
| 3 — the base classes | **Done.** `ButtonBase`, `ListControl`, `UpDownBase`, `ToolStripDropDownItem`, with the concrete controls reparented onto them. |
| 4 — ToolStrip rendering and item parity | **Done.** `ToolStripRenderer` (41/41), then `ToolStripItem`/`ToolStrip` as one pass; 135 gaps closed, 14 tests. |

Baseline: **1,905 → 1,450**.

Two things worth carrying forward:

- **Generate, do not transcribe.** Item 1's values and item 2's shapes both came from the reference
  assembly. That paid for itself immediately: a hand-written test asserting `SearchDirectionHint` as
  `0..3` failed against the generated `37..40`, which are the Win32 arrow-key codes upstream actually
  uses. The generated values were right and the human assertion was wrong.
- **Reparenting is not free.** Item 3's first pass deleted the derived controls' members so they would
  inherit from the new base — which silently discarded real behaviour (`Button.AutoEllipsis` runs a
  layout transaction and invalidates; the base is a plain auto-property). The derived implementations
  are now kept as `override`s, and a test calls through the base type to prove it.

### What item 4's second half found

`ToolStripItem`/`ToolStrip` were done as one pass ([`ToolStripParity.cs`](../src/Majorsilence.Forms/ToolStripParity.cs)),
since most of what was missing is the `Control`-parity surface — accessibility properties, the drag
family, `Anchor`/`Dock`, the `*Changed` events — which fragments badly if taken type by type. Each
member is classified in that file's header as **Real** (backed by state this layer has), **Raisable**
(a real event with a protected raiser) or **Stored** (round-trips, not yet consulted by the drawing
path), so a reader never has to guess which they are looking at.

It also surfaced a live bug the gap count could not see: **`ToolStripItem.Owner` returned null for
every item on a `ToolStrip`.** It read `ParentControl`, which only `MenuDropDown` ever assigns; an
item added to a strip hangs off that strip's *root item* and has no `ParentControl` of its own. It
now walks the owning-control chain, which is what makes `GetCurrentParent`, `IsOnDropDown` and
`GetItemAt` mean anything. This is the third time in this plan that a member which merely *existed*
was wrong — the same class of defect as the 126 `VALUE` mismatches.

### Next

With item 4 closed, the largest remaining concentrations are `DataGridView` (83 members),
`ToolStripTextBox` and `TextBoxBase` (38 each), `ListView` (34) and `AccessibleEvents` (32).
`DataGrid`/`DataGridTableStyle` (46/42) stay low priority — they are the .NET 1.x controls.

## Suggested order

1. **The 126 `VALUE` mismatches.** Correctness bugs, mechanical fix, generate from upstream.
2. **The 88 `EventHandler` delegates + 54 `EventArgs`.** Unblocks designer files; near-zero risk.
3. **The missing base classes.** `ButtonBase`, `TextBoxBase`, `ListControl`, `UpDownBase` — these gate
   whole categories of migrated code that member-level work cannot reach.
4. **`ToolStripItem` / `ToolStrip` / `ToolStripRenderer`.** Toolbars and menus are in nearly every
   LOB app, and `ToolStripRenderer` being entirely absent means custom chrome is impossible.
5. **`DataGridView` members.** Biggest single count, and the control most likely to carry an app's
   core UI.

Everything here follows the same definition of done as the drawing plan: real computed values in
tests rather than existence checks, `COMPATIBILITY_MATRIX.md` corrected where it overstates, and the
baseline regenerated so the gap set provably shrank.
