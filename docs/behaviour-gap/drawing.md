# Drawing — findings

## Summary
The drawing area splits sharply in two. `Majorsilence.Forms.Drawing.Common` — the GDI+ replacement — is largely real: `Region` algebra, `GraphicsPath`, `Matrix`, `LockBits`/`UnlockBits`, `ImageAttributes` colour matrices, EXIF property items and GIF frame selection are all genuinely implemented, and all five members `docs/gdi-gap-plan.md` flagged as hollow have since been fixed (re-verified below). The failures are concentrated one layer up, in `Majorsilence.Forms`' own `Graphics`, `ControlPaint`, `TextRenderer` and `VisualStyleRenderer`, and they cluster into four dominant patterns: (1) a pooled *fast path* that silently drops fidelity the slow path has — `GetStrokePaint` copies three fields of a `Pen` and every dashed line in the framework draws solid, while `Pen.CreatePaint()` two files away builds the correct paint; (2) *measure and draw computed by different code that disagrees* — `MeasureString` wraps and `DrawString` never does, `TextRenderer.MeasureText` measures a 9pt font at 9 pixels while `DrawText` draws it at 12, so anything auto-sized from a measurement is clipped; (3) *region- and path-shaped arguments collapsed to a bounding rectangle*, which is why clipping to a rounded-rect path gives square corners; and (4) *state properties stored and never read* — `InterpolationMode`, `CompositingMode`, `PageUnit`, `TextRenderingHint`, `GraphicsPath.FillMode`, `ImageAttributes.NoOp`. Twenty `ControlPaint.Draw*` chrome methods are empty bodies and are rated as one group with an implementation plan (GFX-01), since they are how owner-drawn migrated controls paint every border, button face, check glyph and drop arrow. 46 findings: **3 P0, 17 P1, 26 P2**, plus ~20 P3 Win32-only members listed briefly. Almost nothing in this area has a test — of the 46, only three name an existing test file, and none of those covers the divergence found.

## Findings
### GFX-01 — `ControlPaint` chrome-drawing family (20 methods) — Cat B — P1 — High
- **Ours:** Twenty public `ControlPaint.Draw*` overloads taking `Majorsilence.Forms.Drawing.Graphics` have literally empty bodies: `DrawBorder`×2, `DrawBorder3D`×3, `DrawButton`, `DrawCheckBox(Graphics,…,ButtonState)`, `DrawComboButton`, `DrawRadioButton(Graphics,…,ButtonState)`, `DrawScrollButton`, `DrawSizeGrip`, `DrawStringDisabled(Graphics,…,StringFormat)`, `DrawMenuGlyph`×2 (`src/Majorsilence.Forms/ControlPaint.cs:178-262`), plus `DrawCaptionButton`, `DrawContainerGrabHandle`, `DrawGrabHandle`, `DrawLockedFrame`, `DrawSelectionFrame`, `DrawMixedCheckBox` (`src/Majorsilence.Forms/MidSizeControlParity.Three.cs:29-53`). Only the `PaintEventArgs`-based `DrawCheckBox`/`DrawRadioButton`/`DrawArrowGlyph`, `DrawGrid`, and `DrawImageDisabled` actually draw.
- **Upstream:** every one of these paints. `DrawBorder` dispatches to `DrawBorderSimple`/`DrawBorderComplex` per `ButtonBorderStyle` (`src/System.Windows.Forms/System/Windows/Forms/Rendering/ControlPaint.cs:553`), the 14-arg overload strokes each side with its own colour/width/style as mitred trapezoids (`:579-640`), `DrawButton`/`DrawCheckBox`/`DrawComboButton`/`DrawRadioButton`/`DrawScrollButton`/`DrawCaptionButton`/`DrawMenuGlyph` all funnel into `DrawFrameControl` (`:1453`) which renders a Win32 `DrawFrameControl` bitmap and blits it, `DrawGrabHandle` (`:1511`) and `DrawSizeGrip` (`:1947`) are pure managed GDI+ line/rect code.
- **Impact:** this is *the* API an owner-drawn migrated control uses to paint its chrome. A `DataGridView`-style custom cell painter, an owner-drawn `ListBox`/`ListView`, a `UserControl` with `ControlPaint.DrawBorder(g, ClientRectangle, …)`, a designer surface, or a custom combo drawing its own drop arrow all render *nothing at all* — no border, no button face, no check glyph, no drop arrow, no size grip. The control looks empty/flat rather than mis-styled, which is the visible, common failure. Our own code is affected: `ControlPaint.DrawVisualStyleBorder` (`MidSizeControlParity.Three.cs:56`) delegates to the no-op `DrawBorder`, and `ExtendedToolkitParity.Two.cs:78` draws a GroupBox frame through it — so that GroupBox has no frame.
- **Fix:** implement as a group against `Graphics`, no glyph font required. (a) Skia primitives, straightforward: `DrawBorder` both overloads (rect stroke per side; `Dotted`/`Dashed` = `SKPathEffect.CreateDash`; `Inset`/`Outset` = 2-tone bevel using `Light`/`Dark` of the colour — port `DrawBorderComplex`), `DrawBorder3D` (map `Border3DStyle` to the classic 2-pixel bevel colour quadruple `ControlLightLight/ControlLight/ControlDark/ControlDarkDark`, honour `Border3DSide`), `DrawSizeGrip` (port the loop at upstream `:1955-1970` verbatim — three diagonal lines per 4px group, `LightLight(backColor)`/`Dark(backColor)`), `DrawGrabHandle`/`DrawContainerGrabHandle`/`DrawLockedFrame`/`DrawSelectionFrame` (filled rect + 1px pen, upstream `:1511-1535`, `:1708`, `:1927`), `DrawStringDisabled(Graphics,…,StringFormat)` (upstream `:2004` — draw at +1,+1 in `LightLight(color)` then at 0,0 in `Dark(color)`; today it is empty while the sibling `IDeviceContext` overload draws). (b) Needs a small vector glyph, still no font: `DrawButton`/`DrawCaptionButton` (bevel + optional glyph), `DrawCheckBox`/`DrawMixedCheckBox` (port upstream's fully-managed `DrawFlatCheckBox`, `:1349`, which is already GDI+-only), `DrawRadioButton(ButtonState)`, `DrawComboButton`/`DrawScrollButton` (reuse the existing `DrawArrowGlyph` triangle logic in `ControlPaint.cs:15`), `DrawMenuGlyph` (check/bullet/arrow — `MenuGlyph` has only 3 values). Honour the `ButtonState` bits: `Inactive` → grey the glyph, `Pushed` → swap bevel light/dark and offset the glyph +1, `Flat` → 1px flat border, `Checked` → fill with the 50% checker pattern.
- **Test:** render each into a headless `Bitmap` over a known solid fill and assert (i) the bitmap is no longer uniform, (ii) the corner/edge pixels of `DrawBorder(…, Color.Red, Solid)` are red, (iii) `DrawBorder3D` top-left pixel != bottom-right pixel (bevel direction), (iv) `DrawButton(state: Pushed)` differs from `Normal`.
- **Tests today:** none (all 20 are listed in `tests/Majorsilence.Forms.Tests/NoOpStubBaseline.txt:34-55` as accepted no-ops).

### GFX-02 — `ControlPaint.Light/LightLight/Dark/DarkDark` — Cat A — P1 — High
- **Ours:** `Light(Color, float percOfLightLight = 10f)` adds `percOfLightLight * 2.55` to each RGB channel and clamps; `Dark` subtracts. `LightLight(c) => Light(c, 40f)`, `DarkDark(c) => Dark(c, 40f)` (`src/Majorsilence.Forms/ControlPaint.cs:325-350`). The percentage parameter is interpreted as **0–100**.
- **Upstream:** `Light(c, p) => new HLSColor(c).Lighter(p)`, `Light(c) => Lighter(0.5f)`, `LightLight(c) => Lighter(1.0f)`, `Dark(c) => Darker(0.5f)`, `DarkDark(c) => Darker(1.0f)` (`…/Rendering/ControlPaint.cs:2319-2330`, `:396-406`). The parameter is a **0.0–1.0 fraction**, and the algorithm is the Win32 HLS one: convert to hue/luminosity/saturation on a 0–240 range, apply `ShadowAdjustment = -333` / `HighlightAdjustment = +500` scaled luma, and convert back (`…/Rendering/ControlPaint.HLSColor.cs:14-172`). Crucially, when the base colour *is* `SystemColors.Control`, `Lighter`/`Darker` short-circuit to the exact `SystemColors.ControlLight`/`ControlLightLight`/`ControlDark`/`ControlDarkDark` values rather than computing (`HLSColor.cs:86-115`, `:140-165`).
- **Impact:** two independent bugs. (1) Unit mismatch: existing WinForms code that calls `ControlPaint.Light(c, 0.5f)` — the documented, common form — gets `+1` per channel here, i.e. a visually identical colour, so every hand-rolled bevel/highlight collapses to flat. Conversely `Light(c, 40f)` upstream would saturate to white. (2) Wrong hue behaviour: linear RGB addition desaturates towards white/black instead of moving luminosity in HLS, so `Dark(Color.Red)` = `(230,0,0)` here vs `(128,0,0)` upstream, and `Light(SystemColors.Control)` = `White` here vs `ControlLight` (`#E3E3E3`, which is *darker* than `Control`) upstream. Anything that builds a 3D bevel from these — and every one of the GFX-01 implementations will — comes out wrong.
- **Fix:** port `ControlPaint.HLSColor` verbatim (it is ~170 lines of integer math with no Win32 dependency), then define `Light(c, p) => new HLSColor(c).Lighter(p)` etc. Add real single-argument `Light(Color)`/`Dark(Color)` overloads mapping to 0.5f rather than relying on a default parameter of 10f — the default-parameter form also means the `Light(Color)` *overload* does not exist for reflection/`Delegate` binding.
- **Test:** `Assert.Equal(Color.FromArgb(255,128,0,0), ControlPaint.Dark(Color.Red))`; `Assert.Equal(SystemColors.ControlDark, ControlPaint.Dark(SystemColors.Control))`; `Assert.Equal(SystemColors.ControlLightLight, ControlPaint.LightLight(SystemColors.Control))`. Pure colour math, no display needed.
- **Tests today:** none.

### GFX-03 — `ControlPaint.DrawFocusRectangle` — Cat A — P1 — High
- **Ours:** both overloads route to `Graphics.DrawFocusRectangle(Rectangle)` and the colour arguments are dropped on the floor (`src/Majorsilence.Forms/ControlPaint.cs:172-176`). That method hardcodes `SKColors.Black`, a 1-on/1-off dash, and strokes the *full* rectangle (`src/Majorsilence.Forms/Graphics.cs:1957-1964`); its own doc comment says "stub".
- **Upstream:** `DrawFocusRectangle(g, rect)` defaults to `(SystemColors.ControlText, SystemColors.Control)`, and the private worker does `rectangle.Width--; rectangle.Height--;` before stroking with `GetFocusPen(color, odd: (rect.X+rect.Y)%2==1, …)` — a 2×2 dither-patterned `TextureBrush` pen whose two colours are derived from the *background* colour so the dots invert against it, with the phase chosen so the corner pixel is always penned (`…/Rendering/ControlPaint.cs:1425-1450`).
- **Impact:** (i) black focus dots are invisible on a dark theme or a dark-backgrounded control — the keyboard-focus indicator disappears, an accessibility regression; (ii) the rectangle is one pixel wider and taller than upstream, so a focus rect drawn at `ClientRectangle` is clipped on the right/bottom edge; (iii) the dash phase is not parity-aligned, so adjacent focus rects don't tile.
- **Fix:** in `Graphics.DrawFocusRectangle`, take fore/back colours, decrement width/height, and build the dash from a 1px-period `SKPathEffect` whose phase is `(rect.X + rect.Y) % 2`. Have `ControlPaint.DrawFocusRectangle(g, rect)` pass `SystemColors.ControlText, SystemColors.Control` and the 4-arg overload pass its arguments through.
- **Test:** headless-render `DrawFocusRectangle(g, new Rectangle(0,0,10,10), Color.White, Color.Black)` on a black bitmap and assert a white pixel exists and that pixel (9,9) is inside the stroke (not (10,10)).
- **Tests today:** none.

### GFX-05 — `ControlPaint.DrawStringDisabled(IDeviceContext, …)` — Cat A — P2 — High
- **Ours:** lightens the colour halfway to white and draws once via `TextRenderer.DrawText` (`src/Majorsilence.Forms/ControlPaint.cs:288-297`).

### GFX-06 — `Graphics.DrawString(…, RectangleF bounds[, StringFormat])` never word-wraps — Cat A — P0 — High
- **Ours:** every `DrawString` path funnels into `DrawString(text, font, brush, float x, float y)`, which lays the run out at a fixed `Unbounded = 1 << 20` width (`src/Majorsilence.Forms/Graphics.cs:1713-1721`). The rectangle overload only clips to `bounds` and then calls that (`:1746-1752`); the `StringFormat` overload aligns a single measured run and calls `DrawStringClipped`, again with the unbounded width (`:1760-1795`, `:1906-1920`). No overload breaks lines at `bounds.Width`.
- **Upstream:** GDI+ `DrawString(string, Font, Brush, RectangleF)` uses `StringFormat.GenericDefault`, whose `FormatFlags` do **not** include `NoWrap`, so text is word-wrapped inside the layout rectangle and clipped vertically (`src/System.Drawing.Common/src/System/Drawing/Graphics.cs`, `DrawString` → `GdipDrawString` with a null format; `StringFormat.GenericDefault` at `src/System.Drawing.Common/src/System/Drawing/StringFormat.cs`).
- **Impact:** the single most visible text bug available. Any migrated code that draws a paragraph, a wrapped cell value, a tooltip body, a report text box, or a multi-line owner-drawn list item into a rectangle gets **one clipped line** instead of wrapped text. It is made worse by the fact that `MeasureString(text, font, layoutArea)` *does* wrap (`Graphics.cs:119-124` → `TextMeasurer.MeasureText(text, face, proposed)`), so an app that measures to size its box and then draws into it gets a tall empty box with one line of text at the top. Measure and draw disagree.
- **Fix:** route `DrawString(…, RectangleF bounds, StringFormat?)` through the same RichTextKit layout `TextMeasurer` uses, with the layout width set to `bounds.Width` unless `format.FormatFlags` has `NoWrap`; apply `Alignment`/`LineAlignment` to the laid-out block rather than to a single measured run; keep `NoClip` off by default (clip to `bounds`). The greedy wrap already written for `MeasureCharacterRanges` (`Graphics.cs:253 LayoutLines`) is the same algorithm — hoist it.
- **Test:** headless-render `"aaa bbb ccc ddd"` in a 40px-wide rect and assert the painted bounding box height ≈ 4 × line height and that ink exists below the first line; assert `NoWrap` gives one line.
- **Tests today:** none for wrapping. `DrawStringFontFallbackTests.cs` covers glyph fallback only.

### GFX-07 — `Graphics.SmoothingMode.Default` antialiases; GDI+ does not — Cat A — P1 — High
- **Ours:** the fill paths and `DrawPath` set `paint.IsAntialias = SmoothingMode != SmoothingMode.None` (`src/Majorsilence.Forms/Graphics.cs:1265`, `:1314`, `:2198`). The default value of the property is `SmoothingMode.Default` (= 0) (`:422`), so **antialiasing is on by default** for every fill, and `HighSpeed` also antialiases. The pooled *stroke* paint (`GetStrokePaint`, `:1336-1343`) never sets `IsAntialias` at all, so the same property has the opposite failure there — see GFX-23.
- **Upstream:** GDI+ maps `Default`, `HighSpeed` and `None` to *no* antialiasing and only `AntiAlias`/`HighQuality` to antialiasing. Our own enum has the correct upstream values (`src/Majorsilence.Forms.Drawing.Common/Drawing2D.cs:1158-1176`: `Default = 0`, `HighSpeed = 1`, `HighQuality = 2`, `None = 3`, `AntiAlias = 4`), which is exactly why `!= None` is the wrong test — `Default != None`.
- **Impact:** every *fill* a migrated app makes without touching `SmoothingMode` — `FillRectangle`, `FillPolygon`, `FillEllipse`, `FillPath`, and every `DrawPath` outline — is antialiased, so edges bleed a half-intensity row into the neighbouring pixel where WinForms produces a hard edge. Adjacent filled rectangles (the standard way a grid or a gradient ramp is painted) develop visible seams, and pixel assertions against WinForms output fail everywhere. Combined with GFX-23 the surface is *inconsistent with itself*: a `FillRectangle` edge is soft while the `DrawRectangle` outline over it is hard.
- **Fix:** add one `private bool Antialias => SmoothingMode is SmoothingMode.AntiAlias or SmoothingMode.HighQuality;` on `Graphics` and use it in all four paint builders (including `GetStrokePaint`, which sets it nowhere today) so the two sides cannot drift again.
- **Test:** `g.FillPolygon(Brushes.Red, triangle)` with default state and assert every painted pixel is exactly `#FF0000` (no partial-alpha edge); then set `SmoothingMode.AntiAlias` and assert intermediate values appear.
- **Tests today:** none.

### GFX-08 — `Graphics.InterpolationMode`/`PixelOffsetMode`/`CompositingMode`/`CompositingQuality`/`TextRenderingHint` — Cat C — P1 — High
- **Ours:** five plain auto-properties, never read anywhere in the assembly (`src/Majorsilence.Forms/Graphics.cs:425-437`; a grep for each name in `Graphics.cs`/`Drawing/SkiaGraphics.cs` finds only the declaration). `SmoothingMode` is the only one of the six that any paint consults.
- **Upstream:** each changes rendering. `InterpolationMode` selects the resampling filter in `DrawImage`; `CompositingMode.SourceCopy` replaces destination pixels instead of alpha-blending; `PixelOffsetMode.Half` shifts sampling by half a pixel (the standard fix for the 1px seam when scaling images); `CompositingQuality` selects gamma-correct blending; `TextRenderingHint` picks aliased / antialiased / ClearType glyph rasterisation (`src/System.Drawing.Common/src/System/Drawing/Graphics.cs`, each property calls `GdipSetInterpolationMode`/`GdipSetCompositingMode`/… on the native context).
- **Impact:** the two that bite hardest are `InterpolationMode.NearestNeighbor` — set by every image viewer/zoom/pixel-art/barcode/screenshot tool so a magnified image stays crisp; here it stays bilinear and comes out blurred and, for barcodes/QR, unscannable — and `CompositingMode.SourceCopy`, used to stamp a pre-composited layer or to clear with a transparent colour; here it alpha-blends, so `Clear(Color.Transparent)` under `SourceCopy` leaves the old pixels. `TextRenderingHint.SingleBitPerPixelGridFit` (chosen for crisp small UI text) is likewise ignored.
- **Fix:** map them where the paints are built. `InterpolationMode` → `SKSamplingOptions` (`Nearest` for `NearestNeighbor`/`Low`, `Linear`+mipmap for `HighQualityBicubic`) on every `DrawBitmap`; `CompositingMode.SourceCopy` → `paint.BlendMode = SKBlendMode.Src`; `PixelOffsetMode.Half`/`HighQuality` → a half-pixel translate on the source rect; `TextRenderingHint` → `SKFont.Edging` (`Alias` for `SingleBitPerPixel*`, `SubpixelAntialias` for `ClearTypeGridFit`, `Antialias` otherwise) and `Subpixel`.
- **Test:** scale a 2×2 checkerboard to 16×16 with `NearestNeighbor` and assert only the two source colours appear (no intermediate values); with `HighQualityBilinear` assert intermediates do appear.
- **Tests today:** none.

### GFX-09 — `Graphics.PageUnit` / `PageScale` — Cat C — P1 — High
- **Ours:** `public GraphicsUnit PageUnit { get; set; } = Pixel;` and `public float PageScale { get; set; } = 1f;`, both plain auto-properties whose own doc comments say "Stub … always Pixel" (`src/Majorsilence.Forms/Graphics.cs:355-358`). Nothing reads either; `TransformPoints` explicitly documents world↔page as the identity because of it (`:583-588`).
- **Upstream:** the page transform is a real part of the pipeline — every coordinate handed to a drawing call is multiplied by the world transform *and then* converted from `PageUnit` to device pixels using `PageScale` and `DpiX`/`DpiY` (`src/System.Drawing.Common/src/System/Drawing/Graphics.cs`, `PageUnit`/`PageScale` → `GdipSetPageUnit`/`GdipSetPageScale`).
- **Impact:** `PrintDocument` and report code is written in `GraphicsUnit.Inch`, `Millimeter` or `Document` — `e.Graphics.PageUnit = GraphicsUnit.Inch; e.Graphics.DrawRectangle(pen, 1, 1, 6, 9);` is the idiomatic printing snippet. Here the unit is stored and ignored, so that rectangle draws 6×9 *pixels* in the top-left corner of the page: the whole print/report output collapses into a speck. `PageScale` is used the same way for zoom in print preview.
- **Fix:** compose a page matrix (`unitToPixel(PageUnit) * PageScale`) into the canvas whenever either property is set, and factor it out of `Transform`/`TransformPoints` so world-space reads stay world-space. `GraphicsUnit` → pixels needs only `DpiX`/`DpiY` (see GFX-10) and the fixed ratios (Point = 1/72", Document = 1/300", Millimeter, Inch, Display = 1/100" for printers).
- **Test:** `g.PageUnit = GraphicsUnit.Inch; g.FillRectangle(Brushes.Red, 0, 0, 1, 1);` on a 96×96 bitmap and assert pixel (95,95) is red.
- **Tests today:** none.

### GFX-10 — `Graphics.DpiX` / `DpiY` — Cat A — P2 — High
- **Ours:** `public float DpiX => 96f;` / `DpiY => 96f`, hardcoded (`src/Majorsilence.Forms/Graphics.cs:315-318`).
- **Upstream:** returns the surface's real horizontal/vertical resolution — the monitor DPI for a screen `Graphics`, the printer's DPI (600, 1200, …) for a printing one, and the bitmap's `HorizontalResolution` for `Graphics.FromImage` (`src/System.Drawing.Common/src/System/Drawing/Graphics.cs` `DpiX` → `GdipGetDpiX`).
- **Impact:** `Font.GetHeight(graphics)`, any point-to-pixel conversion an app does itself (`points * g.DpiY / 72`), and all printer layout are computed at 96 DPI regardless of the actual device. On a printing surface this is off by 6×–12×; on a HiDPI screen by the scale factor. It also silently defeats the fix for GFX-09, since a page-unit conversion needs a real DPI.
- **Fix:** return the source image's resolution when `_sourceImage` is non-null, the control's device DPI otherwise (the framework already tracks per-control DPI for `LogicalToDeviceUnits`), and the printer resolution for print graphics.
- **Test:** `bmp.SetResolution(300, 300); Graphics.FromImage(bmp).DpiX == 300f`.
- **Tests today:** none.

### GFX-11 — `Graphics.IsVisible(...)` all overloads return `true` — Cat B — P2 — High
- **Ours:** `IsVisible(Point)`, `IsVisible(Rectangle)` and `IsVisible(RectangleF)` are `=> true` (`src/Majorsilence.Forms/Graphics.cs:1178-1184`), and every other overload — `IsVisible(PointF)`, `IsVisible(float,float)`, `IsVisible(int,int)`, `IsVisible(float,float,float,float)`, `IsVisible(int,int,int,int)` — resolves into one of those three (`:1048-1062`), so the whole family is a constant.
- **Upstream:** tests the point/rectangle against the *visible clip region* and returns false when it falls outside (`src/System.Drawing.Common/src/System/Drawing/Graphics.cs`, `IsVisible` → `GdipIsVisiblePoint`/`GdipIsVisibleRect`).
- **Impact:** the idiomatic owner-draw cull `if (!e.Graphics.IsVisible(itemBounds)) continue;` never skips anything, so a virtual list/grid paints every row on every invalidate — an O(n) redraw where WinForms is O(visible). For a 100k-row grid that is a visible hang, not a slowdown. Code that uses it as a *predicate* (e.g. deciding whether a tooltip anchor is on screen) gets a wrong answer outright.
- **Fix:** implement against `_canvas.LocalClipBounds` (`SKRect.IntersectsWith` for rects, `Contains` for points); the canvas already tracks the clip and `ClipBounds` reads it.
- **Test:** `g.SetClip(new Rectangle(0,0,10,10)); Assert.False(g.IsVisible(new Rectangle(50,50,5,5))); Assert.True(g.IsVisible(new Rectangle(1,1,5,5)));`
- **Tests today:** none.

### GFX-12 — `Graphics.IntersectClip(Region)` replaces instead of intersecting — Cat A — P1 — High
- **Ours:** `public void IntersectClip(Region region) => SetClip(region);` (`src/Majorsilence.Forms/Graphics.cs:1045`). `SetClip` *replaces* the clip (it unwinds to the pre-clip baseline first, `:469-505`), so `IntersectClip(region)` **widens** the clip whenever the region is larger than the current one. The `Rectangle`/`RectangleF` overloads (`:1123-1140`) are correct — only the `Region` one is wrong, so the bug is easy to miss.
- **Upstream:** `IntersectClip(Region)` calls `GdipSetClipRegion(…, CombineMode.Intersect)` — it can only ever narrow (`src/System.Drawing.Common/src/System/Drawing/Graphics.cs`, `IntersectClip`).
- **Impact:** nested painting that narrows the clip by region (a scroll viewport intersecting a cell rectangle, a themed renderer intersecting a rounded-corner region) instead *escapes* the parent clip and paints over its siblings — the classic "control draws outside its bounds" corruption. Being a widening rather than a narrowing, the damage is visible and hard to attribute.
- **Fix:** `=> SetClip(region, CombineMode.Intersect);` — the machinery already exists at `:1019`.
- **Test:** `g.SetClip(new Rectangle(0,0,10,10)); g.IntersectClip(new Region(new Rectangle(0,0,100,100))); Assert.Equal(new RectangleF(0,0,10,10), g.ClipBounds);`
- **Tests today:** none.

### GFX-13 — Clip regions are reduced to their bounding rectangle — Cat A — P1 — High
- **Ours:** `SetClip(Region, CombineMode)` uses `region.GetBounds(this)` (`src/Majorsilence.Forms/Graphics.cs:1019-1023`); `ExcludeClip(Region)` uses `Rectangle.Round(region.GetBounds(this))` (`:1171-1175`); `SetClip(Graphics)` copies the source's `LocalClipBounds` (`:1032-1039`); the `Clip` getter always returns a `Region` built from one rounded rectangle (`:1146-1158`). `SetClip(GraphicsPath, CombineMode)` discards the combine mode entirely and calls `SetClip(path)` (`:1014-1016`); `SetClip(Graphics, CombineMode)` likewise (`:1041-1043`). `SetClip(RectangleF, CombineMode)` silently falls back to `Replace` for `Union`, `Xor` and `Complement` (`:998-1011`, documented).
- **Upstream:** the clip is a real region and every combine mode is honoured; `Graphics.Clip` round-trips a non-rectangular region exactly (`src/System.Drawing.Common/src/System/Drawing/Graphics.cs` `SetClip`/`Clip`; `src/System.Drawing.Common/src/System/Drawing/Region.cs`).
- **Impact:** (i) clipping to a rounded-rectangle or ellipse path is *the* way custom controls get rounded corners — here they clip to the bounding box and the corners are square; (ii) the save/restore idiom `var saved = g.Clip; g.SetClip(x); …; g.Clip = saved;` restores only the bounding box, so a previously non-rectangular clip is widened on restore and later drawing leaks; (iii) `ExcludeClip(Region)` excludes the whole bounding box, so excluding an L-shaped or multi-rect region blanks far more than intended — this is how "punch a hole for the child control" transparent painting is written.

- **Tests today:** `tests/Majorsilence.Forms.Tests/WindowRegionTests.cs` (integer cases only).

### GFX-45 — `Region.Transform` rasterises without the bounds clip the rest of the class uses — Cat A — P2 — Medium
- **Ours:** `Transform(Matrix)` does `region.SetPath(transformed)` with the one-argument overload (`src/Majorsilence.Forms.Drawing.Common/Region.cs:235-242`), while the constructor and `Combine(GraphicsPath, …)` both go out of their way to pass an explicit bounds-derived clip, with a long comment explaining that the unclipped form rasterises against the whole coordinate space and cost "tens to hundreds of milliseconds" per call during a drag (`:41-59`, `:277-300`).
- **Upstream:** `Region.Transform` applies the matrix to the region directly, at constant cost (`src/System.Drawing.Common/src/System/Drawing/Region.cs`, `Transform` → `GdipTransformRegion`).
- **Impact:** the same pathology the class already documents and works around elsewhere, left in one method — and for an infinite region (bounds ±2²⁸) the boundary path is astronomically large, so a `Transform` on a default-constructed `Region` is a hang or an out-of-memory rather than a slow call. Anything that scrolls or zooms a clip region by transforming it hits this.
- **Fix:** compute the transformed path's bounds and pass an explicit clip, exactly as `BoundsClip` already does at `:301-310`; special-case an infinite region to stay infinite.
- **Test:** `var r = new Region(); r.Transform(Matrix.Identity)` completes in well under a second and `r.IsInfinite()` is still true.
- **Tests today:** none.

### GFX-46 — `SystemFonts`: seven of the eight fonts are the same font — Cat A — P2 — High
- **Ours:** `DialogFont`, `IconTitleFont`, `MenuFont`, `MessageBoxFont`, `SmallCaptionFont`, `StatusFont` and `CaptionFont` all call the same `Create()` and return `Theme.UIFont.FamilyName` at a hardcoded `9f` points (`src/Majorsilence.Forms/SystemFonts.cs:20-80`). Only `DefaultFont` differs (`Microsoft Sans Serif`/`sans-serif` at 8.25pt, correctly).
- **Upstream:** each comes from a different field of `NONCLIENTMETRICS`/`SystemParametersInfo` and they genuinely differ — most visibly `SmallCaptionFont`, which is smaller than `CaptionFont`, and `DialogFont`, which upstream maps to the shell dialog font (`src/System.Drawing.Common/src/System/Drawing/SystemFonts.cs`).
- **Impact:** mild but pervasive: a form whose small-caption chrome is sized from `SmallCaptionFont` gets full-size text, so tool-window title bars and any control that distinguishes the two look uniform where Windows shows a hierarchy. The 9pt pin is a deliberate and well-reasoned choice (see the comment at `:12-20`) — the divergence is that the *relative* sizes are gone, not the absolute one.
- **Fix:** scale the derived fonts off the base: `SmallCaptionFont` at ~8pt, keep the rest at 9pt, and take the family from the platform's UI font where one is discoverable.
- **Test:** `Assert.True(SystemFonts.SmallCaptionFont.SizeInPoints < SystemFonts.CaptionFont.SizeInPoints);`
- **Tests today:** none.

## Low-priority / Win32-only (P3) — one line each
- `Graphics.GetHdc()` / `ReleaseHdc()` / `ReleaseHdcInternal()` — return `IntPtr.Zero` / no-op (`Graphics.cs:1232-1238`); there is no GDI device context behind a Skia canvas, and `Zero` is the failure value a Win32 caller already checks.
- `Graphics.FromHdc(IntPtr)` / `FromHwnd(IntPtr)` — return a canvas-less `Graphics` that silently swallows every draw (`Graphics.cs:66-69`); no HDC/HWND exists. Arguably should throw like `Image.FromHbitmap` does, for consistency.
- `Graphics.CopyFromScreen(…)` ×3 — no-op (`Graphics.cs:1241-1251`, `NoOpStubBaseline.txt:86-88`); screen capture needs a platform screen API, not a drawing one. Would be implementable per-OS if an app needs it.
- `Graphics.Flush()` / `Flush(FlushIntention)` — no-op (`Graphics.cs:573-576`); nothing is batched, so there is genuinely nothing to flush.
- `Graphics.AddMetafileComment(byte[])` — no-op (`NoOpStubBaseline.txt:85`); only meaningful while recording an EMF.
- `Graphics.GetNearestColor(Color)` — identity (`Graphics.cs:582`); correct, since every surface here is 32bpp and upstream is also the identity on a 32bpp surface.
- `Graphics.TextContrast` — stored (`Graphics.cs:567`); it is a ClearType gamma knob with no Skia equivalent. Default 4 matches upstream.
- `ControlPaint.DrawReversibleFrame` / `DrawReversibleLine` / `FillReversibleRectangle` — no-op (`MidSizeControlParity.Three.cs:80-86`); these XOR onto the screen DC so a second draw erases the first. With no screen DC there is nothing to XOR against, and drawing something un-erasable would be worse. A rubber-band overlay is the portable replacement, and belongs in the control layer, not here.
- `ControlPaint.CreateHBitmap16Bit` / `CreateHBitmapColorMask` / `CreateHBitmapTransparencyMask` — return `IntPtr.Zero` (`MidSizeControlParity.Three.cs:93-99`); a GDI bitmap handle cannot be invented.

- `Image.FromHbitmap` / `Icon.FromHandle` / `Font.FromHdc` / `Font.FromHfont` — throw `PlatformNotSupportedException` with a clear message (`HandleInterop.cs:55-95`); honest and correctly asymmetric with `Font.ToHfont()`/`Region.GetHrgn()`, which return `IntPtr.Zero`.
- `Icon.ExtractAssociatedIcon(string)` — returns null (`HandleInterop.cs:76-80`); the file→icon association is a Windows shell service. Could be backed by the freedesktop MIME database / `NSWorkspace` if it ever matters.
- `Image.SaveAdd(…)` ×2 — no-op (`Image.cs:171-174`); Skia's encoders write one image per file, so multi-frame TIFF/GIF authoring has no backend.

## Systemic patterns
- **A fast path that skips the slow path's fidelity.** The single highest-yield pattern here. `Graphics.GetStrokePaint` was written as a pooled-`SKPaint` optimisation and copies three fields, while `Pen.CreatePaint()` — used by exactly one method, `DrawPath` — copies everything (GFX-23). Same shape in `DrawImage`: the callback overloads forward to the attribute-less implementation while their no-callback siblings honour attributes (GFX-15). Sweep: make every draw call go through *one* paint builder, and let the pool cache the built paint keyed on the pen rather than rebuilding a partial one.
- **Measure and draw computed by different code, and they disagree.** `Graphics.MeasureString` wraps, `Graphics.DrawString` does not (GFX-06/GFX-20). `TextRenderer.MeasureText` measures at `SizeInPoints`, `TextRenderer.DrawText` draws at `PixelSize` (GFX-25). `TextRenderer.MeasureText` wraps by default, upstream does not (GFX-27). Every one of these produces a control sized for text it does not contain. Sweep: route all four through one layout function that takes the format flags, and add a test asserting `Measure(x) == BoundsOf(Draw(x))` for a matrix of flags.
- **The percentage/fraction and point/pixel unit bugs are the same bug twice.** `ControlPaint.Light(c, 10f)` treats the parameter as 0–100 where upstream uses 0–1 (GFX-02); `TextRenderer.MeasureText` treats points as pixels (GFX-25). Both are silent, both are ~4×/1.33× off, and neither has a test. Any parameter carrying a unit in this area deserves an explicit conversion function and a named test.
- **Region- and path-shaped arguments collapsed to a bounding rectangle.** `SetClip(Region)`, `SetClip(Graphics)`, `ExcludeClip(Region)`, the `Clip` getter, and `SetClip(GraphicsPath)` (which flattens curves to control points) all reduce the shape (GFX-13, GFX-24). `SKCanvas.ClipRegion`/`ClipPath` and `GraphicsPath.ToSKPath()` already exist and are used elsewhere in the same file — this is unfinished work, not a platform limit.
- **`CombineMode` accepted and dropped.** `SetClip(GraphicsPath, CombineMode)`, `SetClip(Graphics, CombineMode)` and `IntersectClip(Region)` all discard or invert the combine semantics (GFX-12, GFX-13). Any overload taking a `CombineMode` should be audited in one pass.
- **Quality/state properties are auto-properties nothing reads.** `InterpolationMode`, `PixelOffsetMode`, `CompositingMode`, `CompositingQuality`, `TextRenderingHint`, `PageUnit`, `PageScale`, `RenderingOrigin` (GFX-08, GFX-09, GFX-17), plus `ImageAttributes.NoOp`/`Threshold`/`WrapMode` (GFX-43) and `GraphicsPath.FillMode` (GFX-41). And because `Save`/`Restore` do not carry them (GFX-16), wiring them up without also widening `GraphicsState` would trade one bug for another — fix those two together.
- **A constant where upstream computes.** `DpiX`/`DpiY` = 96, `IsVisible(...)` = true, `IsVisibleClipEmpty` = false, `Image.PixelFormat` = `Format32bppArgb`, `Image.Flags`, `VisualStyleRenderer.IsSupported`/`IsElementDefined` = false. Each is defensible in isolation; together they mean a caller cannot distinguish "not supported" from "the answer happens to be that".
- **Two members that must agree, that don't.** `Application.RenderWithVisualStyles` vs `VisualStyleRenderer.IsSupported` (GFX-38); `CheckBoxRenderer.IsSupported`/`ScrollBarRenderer.IsSupported` (`true`) vs `VisualStyleRenderer.IsSupported` (`false`). Upstream derives one from the other; here they are independent literals. Worth a test that asserts the invariant rather than the values.
- **Copy constructors and `Clone` that drop metadata.** `Image.Clone` and `Bitmap(Image)` lose resolution, raw format, property items and tag (GFX-32); `ImageAttributes.Clone` loses `Threshold`/`NoOp`/`OutputChannel` (GFX-43). Whenever a field is added to one of these types, the clone is the thing that gets forgotten — a reflection-based "every field is copied" test would catch the whole class.
- **`ControlPaint`'s empty chrome family is the single largest concentrated gap** (GFX-01, 20 methods). It is worth treating as one work item rather than twenty: about two-thirds need only rectangles, lines and the existing `Light`/`Dark` helpers, and the remaining glyphs (check, bullet, arrow, close) are small vector paths, three of which already exist in this very file as the `PaintEventArgs`-based overloads. Fixing GFX-02 first is a prerequisite, since every bevel is built from it.
